### 1b. 关于「越改问题越大」的说明

用户观感与改动性质有关，需区分两类：

- **真缺陷**（本轮已修，见上表）—— 这些在本轮之前就存在，不是新引入的。
- **观感变化**：视口固定 390 后，窄屏（320dp）整页等比缩到 82%，宽屏（430dp）放大到 110%。
  同一套布局在不同手机上**字号绝对大小不同**。这是"一次改完、所有手机一致"方案的固有代价，
  换来的好处是任何机型都不会出现错位/溢出。
  若用户更希望"每台手机字号一致"，需改为 `width=device-width` 方案，
  但那会退回到"按机型逐页调 CSS"的模式（风险高，且已验证的矩阵全部作废），**需用户明确决定**。

### 3. 通知栏
已修：`mediaId` 补上后，真机点通知栏按钮能触发回调（实测）。

**2026-09-29 补修进度条显示 00:00-00:00**（详见 `02-改动清单.md` G 节）：

- **根因**：Capacitor 的 `PluginCall.getLong()` 对 JS 数字（经桥是 `Double`）不做转换、直接返回 null，
  于是 `show({duration})` 里的时长**根本没进原生** —— `METADATA_KEY_DURATION` 与 `PlaybackState` 全是 0。
  用 `dumpsys media_session` 实测确认（改前 `position=0, buffered position=0`）。
- **修复**：新增 `readLong()` 按 `Number` 取参数；新增 `setProgress` 插件方法 + JS 侧按秒级节流推送进度；
  `PlaybackState` 不再用 `PLAYBACK_POSITION_UNKNOWN`。改后实测 `position=150000 / buffered=211000`，与推送值一致。
- **顺带修掉一个真 bug**：`hide()` 只 `cancel()` 通知、**从不停前台服务**，导致清空播放列表后通知一直赖着。
  已改为先 `stopService` 再 `cancel`，并给 `MediaPlaybackService.onDestroy` 补 `stopForeground(REMOVE)`。
  实测 `hide()` 后 NotificationRecord 条数归 0、服务退出。

**需用户复测**：用他们指定的曲目（"Bang Bang Bang"）确认进度条走字、拖动与按钮都正常。
> 注：我在测试中**没有对用户账号做任何写操作**（未点赞/未加歌单/未动云盘），
> 只是往页面本地内存塞了测试数据。用户对此有顾虑，后续测试请注意。

## 二、已定位但未修的

### 1. ~~`MUSIC_U` cookie 会丢（★ 值得查）~~ ✅ 2026-09-28 已修复

> **修复**：真正原因不在 cookie 存储，而在两条"误清登录态"的路径——
> ① `request.js`：任何请求（包括没带 MUSIC_U 的匿名请求）收到 301/401/403 都触发全局登出；
> ② `accountSession.js`：启动水合用户信息失败（冷启动 Node 未就绪、请求超时）也会清空登录态。
> 已分别加守卫（`shouldTriggerAutoLogout` / `isAuthError`），只有"确实带了登录 cookie 仍被拒绝"
> 才清理。验证：登录后重启 App、重启模拟器（等同手机重启），`MUSIC_U`/`__csrf`/用户信息全部保留。
> 以下为修复前的原始分析（留档）。

- **现象**：真机上 `document.cookie` 里的 `MUSIC_U` 会消失，但 `userStore.user` 还在
  （头像仍能加载）
- **影响**：`isLogin()` 只查 cookie → 出现"看着已登录、实际 `isLogin()` 为 false"
  的不一致状态，影响需要登录的页面与接口
- **推测**：可能与 `request.js` 的 `triggerAutoLogout`（收到 301 时清 cookie）
  或 WebView 的 cookie 持久化有关，未深查
- **相关代码**：`src/utils/authority.js` 的 `isLogin()` / `clearLoginCookies()`，
  `src/utils/request.js` 的 `triggerAutoLogout`

### 2. 后台音频是否连续（未实听确认）
- 已验证：前台服务与通知**不再被系统掐掉**（`isForeground=true`，暂停时也存活）
- **未确认**：App 退到后台后，**音频本身是否连续播放**
  （取决于 Capacitor 退后台时 WebView 是否继续跑 JS；Capacitor 的
  `Bridge.onPause()` 经查**没有**调用 `webView.onPause()`，所以理论上应该继续）
- **需要**：用户戴着耳机实听确认

### 3. 波形是合成包络，不是真实频谱
- 原因：Howler 在移动端退化为 HTML5 `<audio>`，唯一可用路径 `captureStream()`
  因音频跨域（CDN 无 CORS 头）拿不到轨道
- **想拿到真实频谱**：把音频也走本地转发层 + 响应加 `Access-Control-Allow-Origin`，
  再配 `Howler.crossOrigin='anonymous'`（改动较大，未做）

### 4. MIUI 的 `System.err` 噪声
```
java.lang.NullPointerException: null receiver
  at miui.systemui.dynamicisland.window.DynamicIslandWindowView.updateDynamicIslandView
  at com.android.systemui.statusbar.notification.mediaisland.MiuiIslandMediaControllerImpl.addDynamicIslandView
```
- 是 **MIUI 自身的灵动岛代码**在渲染媒体卡片时抛的，应用侧改不了
- 补上 `mediaId` 后功能已正常，但该警告仍会出现（暂不影响使用）

## 三、长期建议

### 1. 冷启动偏慢
每次启动都要把 **4800+ 个运行时文件**从 APK 解压到 App 私有目录（实测首次要 60s+）。
可考虑：
- 首次解压后打标记跳过
- 精简 `mobile-runtime/` 的依赖

### 2. `scripts/prepare-mobile-runtime.cjs` 已废弃
早期"把运行时放进 `dist/nodejs`"的方案，被 `build-android.cjs` 的 `copyRuntime()`
取代。**已核验全工程无任何引用**，确认无需留档即可删除（无 git，删了不可恢复）。

### 3. 目前只出 debug APK
用 debug keystore 签名。要发布需配置 release 签名。

### 4. 接入 `cap sync` 的替代方案
现在依赖"生成物常驻在构建目录"。若构建目录被清空或换机器，需先手动跑一次
`npx cap sync android` 把 `capacitor-cordova-android-plugins/`、
`assets/public/`、`assets/capacitor.plugins.json` 等生成出来，否则 gradle 会报错。
（详见 `参考-Android构建与架构.md`）

## 四、环境相关的坑（非代码问题，但会挡住你）

1. **本机没有可用的模拟器**：Hyper-V/WHPX 均为 Disabled，AEHD 驱动未装且装驱动需
   管理员权限。**只能用真机**（用户插 USB）。
2. **本机有批量删除保护**：单轮删超过 50 个文件会被拦，且按轮次累计。
   清理产物**优先"移动"而不是"删除"**（`Move-Item` 不触发）。
   另：目标文件名含中文时回收站会因路径乱码失败，需先改 ASCII 名。
3. **模型读不了图片时**：用 PIL 做像素分析 + 比例映射定位（见 `01-技术记录` 第四节）。
